# EC 代理版双上下文持久化与召回设计决议

> 状态：**已定案（本次讨论产出）**，尚未实现。
> 适用范围：`ever-context-hook`（EC 的 ww3 拦截器形态，纯 Rust）。
> 前置背景：代理形态没有 Pi 的 JSONL 与分支 API，只能从下游 agent 的输入重建双侧上下文。

---

## 0. 核心原则

1. **不信任下游传来的任何对话 ID**。完全依赖对话指纹（内容摘要）寻址。
2. **代理自建 JSONL**，格式参考 Pi，但双侧上下文（agent 侧原文 + 投影产物）**并存于同一文件**。
3. **树状分叉是第一公民**：通过 `message_id` + `parent_id` 支持任意分叉。
4. **召回范围 = 当前树杈（叶子到根的祖先链）**，不是全树。
5. **EC 对下游行为零假设**：
   - 无法区分 subagent 与主 agent → **只有一条 user 消息 = 新开对话**。
   - 下游裁剪/滚动/压缩上下文 → EC 无法感知 → **作为新对话处理**（定位失败即 fork）。
   - 首条 user 定位前**跳过前导 system 消息**（有些客户端把 system 内联为 messages[0]）。

---

## 1. 会话寻址

### 会话 ID = 首条 user 全文的 SHA

- 会话 ID = `sha256(首条 user 消息的 content 全文)` 的十六进制截断（16 字符）。
- **对新对话、老对话一律如此**：收到任意一次含完整上下文的请求，取首条 user 计算 SHA，即为会话 ID，用于定位 JSONL 文件。
- 不依赖下游传来的 conversation_id（下游可能根本不传、或传了也不稳定）。

### JSONL 文件路径

```
<data_root>/sessions/<session_id>.jsonl
```

- `<data_root>` 由插件数据目录决定（ww3 的 `--data` 参数，或环境变量 `EC_DATA_ROOT`）。
- 每个会话一个文件，分叉不另建文件（树结构在文件内部用 parent_id 表达）。

---

## 2. JSONL 记录 schema

### 消息记录（user / assistant / tool_result）

```jsonc
{
  "id": "a1b2c3d4e5f6a1b2",   // message_id，见 §2.1
  "parent_id": "9f8e7d6c5b4a3f2e", // 前一条消息的 message_id；根消息为 null
  "role": "user",              // user | assistant | tool_result
  // content 按角色不同：
  "content": "帮我写个函数",    // user / assistant 的正文
  // 或 assistant 的工具调用：
  "tool_calls": [{"id":"call_1","name":"bash","arguments":"..."}],
  // 或 tool_result：
  "tool_call_id": "call_1",
  "tool_name": "bash",
  // —— 投影产物（可选，见 §3）——
  "ec": {
    "state": "summary",        // raw | summary | index_only | omitted
    "title": "初始需求评估",
    "summary": "用户要求...",
    "highlights": ["凭据：...", "核心契约：..."]
  }
}
```

### 2.1 message_id 计算（关键：必须含 parent_id）

```
message_id = sha256(feature_text + parent_id) 截 16 字符
```

- `feature_text` = 按角色拼接的规范化文本：
  - user：`"user:" + content`
  - assistant：`"assistant:" + content`（无工具调用时）；有工具调用时拼接 `tool_calls[].name + arguments`
  - tool_result：`"tool_result:" + tool_call_id + ":" + content`
- **`parent_id` 必须纳入哈希**。否则同一对话中重复内容（如连续两个 "继续"）会产生相同 message_id，树结构被破坏。
- 根消息（首条 user）的 parent_id 视为空串。

### 2.2 定位规则：从请求定位到 JSONL 行

收到下游请求 `messages[]`（完整上下文）后：

1. **剥离前导 system**：若 `messages[0].role == "system"`（或 `developer`），跳过，取第一条 `role == "user"` 的消息作为"首条 user"。
2. **单条 user 判新对话**：若整个 messages 只有一条 user（且无 assistant/tool 历史），视为**新开对话**——此时不定位，直接新建 JSONL。
3. 取首条 user 计算会话 ID → 定位 JSONL 文件（不存在则新建）。
4. 取请求中**最后一条原生消息**（user / tool_result / assistant 皆可），计算其 `(feature_text)` 在 JSONL 中定位到行。
   - 若内容重复导致单条定位歧义：改用**序列匹配**——要求请求尾部连续 N 条消息的 `(role, feature_text)` 序列在 JSONL 中连续吻合（N 从 3 递增到全部）。
   - **定位失败 = 新对话处理**（诚实降级，不硬猜——与 BC 的 fork semantics 一致）。
5. 从定位到的行沿 `parent_id` 上溯，得到**从根到当前叶子的完整祖先链**。
6. 祖先链 = agent 侧上下文的权威视图（用于增量估算、压缩触发、recall 范围确定）。

---

## 3. 投影产物的持久化位置

**投影产物（标题+摘要+精华）挂在触发压缩的那条消息记录的同一行**，新加 `ec` 字段。

- 在某次 tool_result（或 user 请求）之后触发压缩，就把压缩结果写到**那条 tool_result（或 user）记录**的 `ec` 字段。
- 意义：压缩发生在哪个时间点，投影产物就锚定在那个时间点。沿 parent_id 上溯时，遇到带 `ec` 字段的记录，即可确定"从根到这里已被压缩成块"。
- `ec.state` 四态（与 Pi 版一致）：
  - `raw`：原文，未压缩
  - `summary`：已压缩成摘要
  - `index_only`：仅剩标题+索引 ID（摘要进一步折叠）
  - `omitted`：完全滚出投影（仅可召回）

### 双侧上下文的同一性

- **agent 侧上下文** = JSONL 中的原始消息（role + content + tool_calls 等）。
- **投影上下文** = JSONL 中"未压缩的尾部原文" + "压缩位置的 `ec` 摘要产物"。
- 两者**在同一个 JSONL 文件里**，永不分裂、永不漂移。

## 4. 树状分叉与 recall

### 4.1 分叉的自然支持

- 每个消息的 `parent_id` 明确指向上一节点。下游 agent 若分叉（回退到某条消息后重新生成），会发来一条新的 messages 序列，其尾部与 JSONL 中已有树结构产生新分叉。
- EC 无需"检测分叉"——它只是把新消息 append 到 JSONL（新消息的 parent_id 指向分叉点），树结构自然形成。
- 分叉点的旧叶子仍是树的一部分，可被 recall 命中。

### 4.2 recall 的搜索范围：当前树杈的祖先链

- **严谨处理**：在本对话中 recall，应搜索"当前树杈"——从当前叶子沿 parent_id 上溯到根的路径，**不是全树**。
- 理由：兄弟分支是不同时间线，召回兄弟分支的内容会让 LLM 看到"未实际发生的对话"，造成混淆。
- 祖先链正是当前对话实际走过的路径，语义正确。

### 4.3 recall 的寻址参数

- recall CLI 命令只需 `--session <session_id>`，**不需要 `--leaf` 参数**。
- 原因：**每次有新的消息产生，parent_id 都会落盘更新**（把当前最新叶子记录在会话的定位信息里）。对 session 做 recall，隐含了"最近一次的 parent_id"。
- 实现方式（暂时方案，已确认）：EC hook 在每次处理请求时，把 `(session_id, 当前叶子 parent_id)` 写入一个**短时定位文件**。`ec-recall --session <id>` 读取该文件得到叶子，沿父链上溯到根，在此范围内搜索。
  - 已知限制：同一会话两个分支并发 recall 时，"当前叶子"可能错乱。**判定为罕见场景，暂接受**，以后优化。
  - 优化方向（未实现）：LLM 显式传 `--leaf`，但需要解决 leaf 值对 LLM 可见的问题（见 §5）。

## 5. 投影注入（向 LLM 暴露的寻址信息）

### 头部注入：session_id + rev（稳定，不破坏前缀缓存）

```
[EC_CONTEXT session=a1b2c3d4e5f6a1b2 rev=3]
```

- `session`：永久稳定，跨轮不变 → 放头部 system 区，不破坏前缀缓存。
- `rev`：只在压缩时变 → 压缩本身必然改变块摘要（前缀本来要失效），rev 变化不造成额外损失。
- **不把 leaf（当前叶子的 parent_id）放头部**——leaf 每轮变化，放头部会破坏前缀缓存。

### 尾部注入：leaf（每轮变化，放末尾天然不破坏缓存）

末尾追加一条投影消息：

```jsonc
{ "role": "user", "name": "ec_meta", "content": "leaf=d4e5f6a1b2c3d4e5" }
```

- 连续 user/user 消息符合 OpenAI Chat Completions 规范（规范只约束 tool 消息必须紧跟 tool_calls，不禁止连续 user）。
- `name: "ec_meta"` 用于标识"这是投影注入消息，不是用户真实输入"，便于后续过滤与防污染。
- 兼容性风险：某些逆向渠道（ww3 承接的 chatglm/raccoon/qwenwork 等）可能对消息序列比 OpenAI 更严格（BC 的 `compat.roles` learn-on-failure 佐证）。**兜底**：注入做成可配置开关，遇到 400 就关闭，退回降级模式（无分叉时 session 足够定位）。

## 6. 压缩触发与 recall 内容的处理

### 6.1 增量估算：跳过 recall 召回内容

- 触发压缩的增量估算（growth nudge / pressure）**必须跳过 recall 召回的内容**，不能重复计入。
- 原因：一旦全文召回，上下文一下增加 10K token，会立刻触发一次压缩，且本次压缩无新内容 → 浪费 + 死循环。
- 识别方式：recall 结果消息带 `name: "ec_recall_result"` 或等价标记，估算时跳过。

### 6.2 压缩提示词：排除 recall 内容

- 压缩提示词中明确要求 LLM：**不要在摘要中包含 `tool_result` 类型为 recall 的内容**。
- 原因：避免同样内容反复进入会话索引（召回的内容已经是历史块的一部分，再摘要一遍就是重复）。

## 7. 超长旧对话（legacy）处理

EC 代理版没有"提前扫描全局已有对话"的过程，每个 JSONL 都是首次遇到对话时现场创建。
对于首次遇到的超长旧对话（blocks 为空 + 投影超软阈值），采用**两阶段**处理：

### 7.1 阶段一：纯规则快速初始化（不调 LLM，不阻塞）

1. **创建 JSONL 树**：请求里的全部原生消息逐条转 MessageRecord（message_id + parent_id 链）。
2. **分段建索引**（Tantivy）：按 target_tokens 累计在消息边界切分，每段建一条索引文档（title/summary 空）。
3. **尾部贴合降级**：降级目标 = `soft_threshold × degrade_target_ratio`（默认 0.6）。
   例如 1M 窗口 → 软阈值 500K → 降级保留 300K，比硬预算更激进，给后续压缩留余量。
4. **不阻塞对话**：降级后正常转发，agent 立即可继续对话。关键词检索也立即可用（正文已分词入索引，只是缺 title/summary）。

### 7.2 阶段二：索引追赶（spawn 独立子进程）

1. **独占锁**：同会话只允许一个追赶进程（`<session>.lock`，含 PID+时间戳过期判断）。
2. **游标**：JSONL 里最后一个带 ec 字段的记录。
3. **逐段追赶**：spawn `ww3-core stdio --hooks none`，关思考，逐段补 title/summary/highlights，写回 JSONL 的 ec 字段 + 更新 Tantivy 索引文档。
4. **追平**：游标之后到保护尾之间没有未折叠消息 → 退出。下一次 prepare 自动用新摘要构建管理区。

### 7.3 关键设计点

| 设计点 | 说明 |
|---|---|
| **降级 ≠ 拒绝** | 超长时先尾部贴合让对话继续，绝不拒绝 |
| **降级目标比硬预算更激进** | soft_threshold × 0.6，留出余量让日常增长交回压缩维护 |
| **state 即游标** | 追平进度 = JSONL 里最后一个带 ec 的记录；重启/分叉自然续跑 |
| **纯规则先行** | 分段和建索引不调 LLM，让 agent 不被阻塞 |

## 8. 并发与锁

代理版是一请求一进程，同一会话可能有多个 hook 进程并发、catchup 子进程也在写 JSONL——必须分层加锁。

### 8.1 需要锁的写操作

| 操作 | 风险 | 锁 |
|---|---|---|
| `append`（handle_stream 响应后追加 assistant） | 与 `set_ec` 并发 retch | JSONL 写锁 |
| `set_ec`（catchup 全量重写 JSONL 补 ec） | 读-改-写整个文件，与 `append` 并发必丢数据 | JSONL 写锁 |
| `import_messages`（prepare 新对话批量导入） | 同上 | JSONL 写锁（内部调 `append`） |
| `index_block` / `index_blocks`（Tantivy 写） | Tantivy 自带 writer lock，LockBusy 报错 | 重试或串行 |
| catchup 整体 | 同会话只能一个追赶进程 | 会话锁（`<session>.lock`） |
| `update_leaf`（原子 rename） | 安全 | 不需要 |

### 8.2 两级锁设计

- **JSONL 写锁**（`<session>.jsonl.lock`）：短持（每行 append 毫秒级），`append`/`set_ec`/`import_messages` 自动获取/释放。
- **会话锁**（`<session>.lock`）：catchup 持有直到追平结束。

### 8.3 过期处理

锁文件格式：`<pid>\n<unix_ts>`。获取时检查：
1. 时间戳超过 30 分钟（`STALE_SECS=1800`）→ 视为过期，删锁重试。
2. 时间戳未过期但 PID 不存活 → 视为过期（进程被强杀后锁残留）。
3. PID 存活且时间戳未过期 → 拒绝重入。

## 9. 与 ww3 hook 契约的映射

| 设计项 | 触发点 |
|---|---|
| 接收下游请求 → 定位 JSONL → 构建投影 | `hook.stream` 的 params.request（当前只读，需 `request.prepare` 契约补充才能改写） |
| 投影注入（头部管理区 + 尾部 ec_meta） | 同上，改写 messages 时一并完成 |
| 事件透传 | `hook.stream` 的事件循环（纯透传，零处理） |
| 响应后：新消息 append JSONL + 更新定位文件 + 压缩判断 | `upstream.end` 时同步完成 |

> `request.prepare` 契约的实现路径见 [`request-prepare-实现路径.md`](./request-prepare-实现路径.md)。

## 10. 已知限制与后续优化

| 限制 | 影响 | 后续方向 |
|---|---|---|
| 并发 recall 的叶子错乱 | 同一会话两分支并发 recall 时，定位文件中的叶子可能过期 | LLM 显式传 `--leaf`（需解决 leaf 可见性） |
| 连续 user 消息的上游兼容性 | 部分逆向渠道可能 400 | 可配置开关，失败降级为仅 session 定位 |
| JSONL 并发 append | 同一会话两请求同时 append | 文件锁，或 OS 层单行近似原子（< PIPE_BUF） |
| 消息重复导致定位歧义 | 单条内容哈希重复时定位错位 | 序列匹配（尾部连续 N 条吻合） |
| 下游截断/滚动/压缩上下文 | EC 完全无法感知，被裁掉的前缀无法恢复 | **作为新对话处理**（见 §0 原则 5） |
| 单条 user 即新对话 | EC 无法区分 subagent 与主 agent | **只有一条 user 提示 = 新开对话**（见 §0 原则 5） |

## 11. 压缩配置

代理版复用插件版的阈值派生公式，不重新发明：

```
contextWindow   = 180_000（默认，按模型查表，见 config.rs）
reserveTokens    = max(16384, round(W × 0.10))      # 硬线预留
softThreshold    = clamp(round(W × 0.50), 100K, 500K)  # 软阈值
degradeTarget    = softThreshold × degradeTargetRatio  # 降级目标（首次尾部贴合保留量，默认 0.6）

# 管理区三区预算（固定）
directoryBudget  = 3_000                            # 目录区（索引ID+标题）
highlightsBudget = 5_000                            # 精华区（契约/凭据/术语）
summaryBudget    = round(softThreshold × 0.30)      # 摘要区
rawBudget        = softThreshold − 三区             # 原文区

# 压缩行为
targetTokens     = 20_000                           # 单块目标
growthNudge      = 50_000                           # 增量压缩触发（自上次压缩累计增量）
minMaintenanceTokens = 20_000                       # 维护最小量
maxBlockTokens   = 80_000                           # 过度合并护栏

# 召回内容处理（防死循环，见 §6）
# 增量估算跳过 ec_recall_result 消息
# 分段 token 估算跳过 recall 记录
# 压缩提示词明确要求 LLM 忽略 recall 结果
```

## 12. 决策记录（本次讨论产出）

1. ✅ 会话 ID = 首条 user 全文 SHA，不信任下游 ID。
2. ✅ message_id = SHA(feature_text + **parent_id**)，parent_id 纳入哈希防碰撞。
3. ✅ 投影产物挂在触发压缩的记录同行，`ec` 字段承载。
4. ✅ 双侧上下文共存于同一 JSONL，单一权威源。
5. ✅ recall 范围 = 当前树杈祖先链，非全树。
6. ✅ recall 寻址只传 `--session`，parent_id 通过定位文件落盘（隐含最近叶子），暂接受并发错乱。
7. ✅ session_id 放头部（稳定），leaf 放末尾 `ec_meta` 消息（每轮变，天然不破坏缓存）。
8. ✅ 增量估算跳过 recall 内容，压缩提示词排除 recall 内容，防死循环。
9. ✅ 未采用"LLM 显式传 leaf"方案（leaf 可见性 + 缓存问题），留作后续优化。
10. ✅ system prompt 内联为 messages[0] 只是兼容性问题，不影响设计（首条 user 定位时跳过前导 system）。
11. ✅ 暂不考虑 tool_call_id 被 agent 篡改（Prime 是小众 agent，优先级低）。
12. ✅ 无法区分 subagent 与主 agent：只有一条 user 提示 = 新开对话。
13. ✅ 下游裁剪/滚动/压缩上下文，EC 完全无法感知，只能作为新对话处理。
14. ✅ 压缩配置复用插件版 `deriveBudget` 公式；`checkpointThreshold` 不迁移（代理版无 Pi checkpoint 机制），改用 `growthNudge`。
15. ✅ 降级目标 `degrade_target = soft_threshold × degrade_target_ratio`（默认 0.6），首次降级比硬预算更激进，给后续压缩留余量。
16. ✅ JSONL 写锁（`<session>.jsonl.lock`）+ 会话锁（`<session>.lock`）两级，含 PID+时间戳过期判断（进程被强杀的锁残留恢复）。
17. ✅ 分段/估算 token 时跳过 `ec_recall_result` 消息（防死循环：召回→膨胀→触发压缩→再召回）。
18. ✅ Tantivy 内嵌（无 sidecar），代理版 schema v1（9 字段，session_id/message_id 独立字段，分支过滤用 message_id ∈ 祖先链）。

BC 的 `MESSAGE-IDENTITY.md` / `SESSION-IDENTITY.md` 两篇文档的核心结论与 EC 代理版对照：

| BC 结论 | EC 代理版对应 | 判定 |
|---|---|---|
| message_id 用内容哈希（role\|contentType\|toolCallId\|toolName\|text）做 join key | message_id = SHA(feature_text + parent_id) | **EC 更优**：parent_id 纳入哈希，从根上消除重复内容碰撞，无需 BC 的实例重编号（_1/_2） |

| tail-window reattach 实测使用率 0 后删除 | 不做任何 mid-chain 匹配 | 一致（BC 用生产数据证明了这条路是死路） |

| 定位必须字节精确，绝不模糊匹配 | 尾部序列匹配必须 (role, feature_text) 精确吻合 | 一致 |
| 定位失败 → fork into fresh session（诚实降级） | 定位失败 → 新对话处理 | 一致 |
